# 性能优化（2026-11-27）

## 播放请求调度

`NativeRequestDispatcher` 的普通池仍最多 8 个 worker，其中普通请求最多占用 7 个，最后一席供带播放序号的 `resolve`、`fallback`、`localPlayback` 使用。预加载和本地文件探测不占用播放预留容量。控制请求继续走独立池。

可用槽优先处理播放请求；连续处理 3 次优先请求后，让可执行的普通请求前进一次。同级请求保持先进先出，队列超时、在途超时不提前释放 worker、取消范围和最新意图校验沿用原逻辑。仅一个 worker 的测试配置不预留容量。

## 海报订阅

`LocalStore.favoriteStatus(id)` 仅发布该剧可见追剧状态的变化。锁定、站源权限、用户切换、恢复备份等统一经过既有通知入口重新核对；无关设置或其他剧目的追剧变化不会触发该卡片构建。

`FavoriteBuilder` 根据 `TickerMode` 订阅或解除订阅，恢复显示时重新读取状态；更换剧目、资料对象、重挂载和销毁均处理监听生命周期。没有订阅者的信号从 store 的跟踪集合移除。

## 下载增量同步

新调用使用 `downloads(delta: true, since: cursor)`。首次及过期游标返回完整 `jobs`；后续返回 `base`、`changed`、`removed` 和新游标，没有变化时只返回游标。游标包含管理器的随机身份与版本号，不复用持久文件的 revision。

原生保留一份不可变任务镜像和有界 ID 日志，最多 16 个版本、2048 个变更 ID。普通进度只标记对应任务，读取时合并；结构与元数据事务重新核对列表，包括失败回滚。落后过多、核心重启、未知游标均回退全量。发布的切片和指针载荷与活记录分离，响应编码及全量排序在锁外完成。旧调用的内容指纹接口仍保留。

Flutter 串行应用下载读取结果，避免并发读取覆盖较新游标；基线不匹配时主动请求全量。只有变化的任务需要模型解析；进度更新复用未变模型及顺序，新增、删除或排序键变化时重新排序。访问权限每次重新过滤。列表引用复制与权限过滤仍与任务总数相关，没有将整条链路描述为常数复杂度。

## 分类缓存预算

原有最多 6 个非当前分类和 10 分钟过期策略继续生效，新增默认 600 条分页结果预算。总量超标时从最久未使用的非当前分类开始回收，并取消其请求；当前分类可以超过预算，保证正在阅读的分页和位置不被截断，此时停止邻页预取。被预算淘汰的邻页在本次浏览中不再重复预取，显式切换或刷新后可重新加载。

可由远端分类接口重新查询的目录完整模型也按剩余预算回收，分类 ID/名称的轻量索引保留。依赖本地目录合成分类的站源保留所需模型，避免产生空分类。因此该预算不是整个进程的内存硬上限。推荐页去掉首张大卡片后的网格列表按源列表身份复用。

## 本机下载同步微基准

Windows amd64，Intel Core i7-8700K，CGO 关闭。`BenchmarkNativeDownloadSync` 对同一任务集合只更新一个任务的进度，比较现有兼容全量路径与增量路径；两者都包括进度写入、快照生成和完整响应 JSON 编码。每组运行 3 次、每次 300ms，下表耗时为三次中位数。

| 任务数 | 全量响应 | 增量响应 | 全量每次耗时 | 增量每次耗时 |
| --- | ---: | ---: | ---: | ---: |
| 100 | 40,333 B | 540 B | 0.966 ms | 0.00745 ms |
| 1000 | 404,833 B | 540 B | 6.364 ms | 0.00720 ms |

1000 任务时每次操作的堆分配中位数为约 1.44 MB（全量）与 3.16 KB（增量）。原始记录：`build/performance-download-bench.log`。复现命令：`go test ./core -run '^$' -bench '^BenchmarkNativeDownloadSync$' -benchmem -benchtime=300ms -count=3`。

该结果只衡量上述合成数据场景的原生同步成本，不包括 Flutter 绘制、视频解码、真实站源网络或整个应用的启动时间，不推导实际帧率或整机内存提升比例。

本次不含安装包构建、Android/Windows 真机帧耗时或整机内存采样。新下载同步需配套重建原生核心；旧核心仍可走完整快照兼容路径。
